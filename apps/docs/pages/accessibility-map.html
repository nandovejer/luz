Every WCAG 2.2 level A and AA criterion, its EN 301 549 clause and the tests in this repository that exercise it. A map of tests, not an audit. Last reviewed on 7 November 2026.

Nobody has audited LUZ against these criteria. This page says, for each one, what a test does about it and what the test leaves out. The accessibility statement has the target, what is checked on every change, what has not been tested and the known issues.

Which clauses apply

EN 301 549 is the European standard for the accessibility of information and communication technology. It is divided into clauses, and only some of them are about what LUZ publishes.

  • Clause 9, Web, applies. LUZ is CSS, scripts and a documentation site made of web pages. Clause 9 takes its requirements from WCAG: version 3.2.1 of the standard from WCAG 2.1 level A and AA, version 4.1.1 from WCAG 2.2. This page maps those criteria. Clause 9 also has 9.6, WCAG conformance requirements, and, in version 4.1.1 only, 9.7, User preferences for web pages. Neither is a row.
  • Clause 10, Non-web documents, is not mapped here. The plain-text files for AI agents, such as llms.txt, and the Markdown copies of the pages are documents provided with web pages and not rendered with them, so clause 10 can apply to them. No test looks at them.
  • Clause 11, Software (Non-web software in version 4.1.1), does not apply. The standard leaves command-line tools such as luz-check out of its scope. LUZ’s scripts run inside web pages, which clause 9 covers.
  • Clause 12, Documentation and support services (Information about products and services in version 4.1.1), applies and is not mapped here. It asks the documentation to list and explain the accessibility features and the support route to give information about them. The Keyboard and ARIA section of each component page and the accessibility statement do part of that. The support route is GitHub’s issue tracker, a third party whose accessibility LUZ does not control.
  • Annex A. In version 3.2.1 it maps the clauses to the Web Accessibility Directive. Version 4.1.1 adds a mapping to the European Accessibility Act (Directive 2019/882). The presumption of conformity under that Directive arrives only once the Official Journal cites the standard. The method of assessment is in Annex C.

How to read the table

Each row is one criterion. The Status column says what the tests do about it.

  • Automated. A test in this repository exercises the criterion, to the extent the Coverage and What is not covered columns say. It does not mean the criterion is met.
  • By hand. A person checked it and wrote down the result and the date.
  • Not tested. No test exercises it.
  • Not applicable. The criterion is about something the site does not have, such as live video or a login. It can still apply to what you build.

The Coverage column is our own judgment of how much of the criterion the tests reach. Broad is most pages and states, Partial is part of the criterion or a sample of pages, Narrow is a small part, and None is no test.

Most of the tests run in Chromium. axe-core, the automated scanner, finds only part of the problems, and no screen reader has been used. For the changes listed in the browser reviews, the specs they name ran in Firefox and WebKit; the statement says how far. Files are named without line numbers, so a row does not go stale when a test moves.

The clause column gives the clause of EN 301 549 version 3.2.1. For these criteria, version 4.1.1 uses the same clause number. Six criteria are new in WCAG 2.2 and are in version 4.1.1 only: the row says New in V4.1.1 and gives their clause. Level AAA criteria are not in the table. Where a criterion has a known issue, the statement lists it.

Criteria

The tables follow the four principles of WCAG: perceivable, operable, understandable and robust. Treat the last two columns as the gap, and test your own pages.
