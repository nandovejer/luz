Example

Experimental. A conversation in the style of a messaging app: tight bubbles, a time beside what was said, and the writer's name for a screen reader. It does not know who answers; this example has a provider of the page's own, with canned answers.

The chat needs JavaScript. Read the documentation.

Known issues

This piece is experimental: its provider contract and its texts can change in a minor release.

  • It has not been tested with a screen reader. The names, the log and the status line are written by the script; how a screen reader reads them has not been checked.
  • No provider ships with the chat. A provider is yours: the chat is the look and the keyboard of a conversation, and it does not know who answers. The example on this page answers from a few canned texts.
  • Without JavaScript, the list of suggested questions shows as plain buttons that do nothing.
  • The edge of the assistant's bubble is below 3:1 against the conversation in light and dark. The bubble is also told apart by its fill and its place, and its text meets its minimum in every mode: see Contrast and focus.
  • The conversation, which can be scrolled and focused, has the browser's own focus outline, not the ring of LUZ.
  • The texts the script writes are in English and Spanish. Any other language needs a data-luz-label-* attribute for each text.
Code Design

Code

Copy the markup

One <luz-chat> holds what the page shows without JavaScript, the questions to try, and, if you like, the provider. Put it where the conversation goes. Everything but the provider, a template and the list of questions is the fallback: it shows when the script has not run, or when no provider can answer.

<luz-chat assistant-name="Ask the docs" enter="send" maxlength="500">
  <p>The chat needs JavaScript. <a href="/docs/">Read the documentation</a>.</p>
  <ul data-luz-chat-suggestions>
    <li><button type="button">How do I install it?</button></li>
    <li><button type="button">How do I change the colours?</button></li>
  </ul>
  <template data-luz-chat-note>Answers can be wrong. Check what matters.</template>
</luz-chat>

The provider is a script of yours. Give it to the element from JavaScript:

import "@luz-ds/catalog/chat";

const chat = document.querySelector("luz-chat");

chat.provider = {
  // messages: [{ role: "user" | "assistant", content }], the whole conversation
  async *ask(messages, { signal }) {
    const reply = await fetch("/your-endpoint", {
      method: "POST",
      headers: { "content-type": "application/json" },
      body: JSON.stringify({ messages }),
      signal,
    });
    if (!reply.ok) throw Object.assign(new Error(`Status ${reply.status}`), { name: "ServiceError" });
    const { text, sources } = await reply.json();
    yield { sources };
    yield text;
  },
};

/your-endpoint stands for a service you run or trust. LUZ does not provide one.

How it works

Load catalog.min.js, as a module. On a page with a <luz-chat> it loads the chat's own file, chat.min.js, when the page is scanned. That file defines <luz-chat>, a custom element in the light DOM (no Shadow DOM). A page may also import @luz-ds/catalog/chat itself, and must for a chat added after the page has loaded.

The chat builds its parts after the fallback: a header with the title and the settings (a native <details>), the conversation, the questions to try, the field with Send, a line under it and a status line for screen readers. The chat stays hidden while no provider can answer and none has anything to say.

The provider

The provider is the first child of the chat that has an ask() method, or whatever you give to chat.provider. A child that is a custom element is waited for until it is defined, up to 5 seconds. A provider set from JavaScript before the chat is defined still works.

A message is text. A body is text or a node, and is cloned each time it is shown.

Sending and answers

  • Sending adds the visitor's message, then the assistant's bubble, with three typing dots until the first words arrive. Words are typed a few at a time; the further behind they fall, the faster, so a long answer does not lag. With reduced motion, or in a hidden tab, they show at once.
  • An answer is shown as Markdown built from DOM nodes, never HTML, so nothing the model writes can add an element, an attribute or a script. It reads paragraphs, headings, bulleted and numbered lists, quotes, code (inline and fenced), bold, italic and struck-through text, and links. Other syntax shows as written.
  • A link in an answer is a link only if it goes to one of the sources of that answer. Any other address shows as its text. A source needs a title and an http or https address; any other is left out.
  • Under a complete answer: its sources, as a list of links, and a button to copy the answer.
  • Stop aborts the signal. What was written stays and joins the history; if nothing had been written, the bubble says “Stopped”.
  • When ask() throws, the bubble says that there was no answer, with the error's name and message after it, and a button sends the same message again. The message that got no answer is not in the history the provider sees next time. Write error messages a visitor can read.
  • The conversation follows the end while the reader is there. If the reader has scrolled up, it stays put and a button says there are new messages. A message the visitor sends is always brought into view.
  • A message by the same writer on the same day sits close to the one before. Each message has the time beside it, and a new day starts with its date.

Where the conversation lives

The conversation lives in memory, in the page, and nowhere else. The chat stores nothing: no cookie, no localStorage, no request of its own. Reloading, leaving the page or clearing the conversation in the settings removes it. Clearing also calls reset() on the provider.

Each call to ask() gets the whole conversation. What the provider does with it, such as sending it to a service, is the provider's, and so is telling your visitors.

Without JavaScript

Nothing of the chat is built. The element is its children: the paragraph and the link you wrote, so write a way to the same help, such as a link to the documentation. The list of suggested questions also shows, as plain buttons that do nothing: this is a known issue. A chat with no provider that can answer, or whose script did not load, shows the same.

Keyboard and ARIA

Everything works from the keyboard.

  • Tab goes to the settings button, the conversation (it can be scrolled with the arrow keys), the questions to try, the field, Send, and Stop while an answer is being written.
  • Enter in the field sends, and Shift + Enter breaks the line. With enter="newline", Enter breaks the line and Send sends. Enter never sends while an input method editor is composing text.
  • The settings are a native <details>: Enter or Space on its button opens and closes it.
  • When an answer ends, fails or is stopped, the focus goes back to the field. After clearing the conversation, it goes to the field too.
  • The chat is a <section> named by its heading. The conversation is role="log", named by the text for conversation, with aria-live="off": an answer is not read word by word.
  • A status line (role="status", hidden from the eye) says “Thinking…” when a message is sent and “Answer ready” at the end; it also says “Stopped”, “Copied”, the text for error, and the message of the provider when its status changes.
  • Each message starts with the name of its writer, hidden from the eye. The time is a <time> with a date. The typing dots are hidden from a screen reader.
  • The field has a label (the text for question). The lists of questions and of sources have names. The settings button is named by an aria-label, and a progress bar or a meter has one.
  • The behaviour above is set by the code. It has not been tested with a screen reader.

Design

When to use

Use the chat where a visitor asks in their own words and expects an answer in a few lines: a help panel, the documentation, a product that explains itself. It fits when you have a provider you trust to answer well, and where a wrong answer costs little.

When not to use

Do not use the chat instead of navigation, search or a page that says the thing plainly. A visitor who can find it by reading does not need to ask.

  • Do not use it where a wrong answer can hurt, such as health, money or the law, unless a person checks the answers.
  • Do not use it to collect data a form should collect. A form says what it asks for, and a conversation does not.
  • Do not use it without a provider, or as a mock-up of a person who is not there.

Do and don't

Writing the content

The visitor is talking to software. Say so, and say what it can and cannot do.

  • Name the assistant for what it is, such as “Ask the docs”, in assistant-name. Do not give it a human name or a face.
  • Use the line under the field (data-luz-chat-note) to say that answers can be wrong, in plain words: “Answers can be wrong. Check what matters.”
  • Write the questions to try as questions, in the visitor's words and the page's language.
  • Write the message of a state in one or two short sentences: what is needed, why, and what the button does. Start the button with a verb: “Start the demo”, “Download the model”.
  • The name and the message of a thrown error are shown to the visitor. Never put a secret, an address of your own or a stack in them.
  • Tell your visitors where their messages go. The chat cannot know.
