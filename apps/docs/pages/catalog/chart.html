Known issues

Four things to know before you rely on it.

  • There is no readout on hover or focus. The figures are in the table, which the button shows; a value that only a pointer could reach would not be reachable by keyboard.
  • It reads the table when it connects, when the table changes and when the box changes size. A table added to the page later, after the page loaded the script, needs the element to be added with it.
  • The plot is drawn left to right in every language, as a time axis is; the table, the title, the legend and the button follow the page’s direction.
  • It has not been tested with a screen reader.
Code Design

Code

Copy the markup

Write the table first, as the page you want a reader to land on: it is the page without JavaScript. The first column is the X axis, a th of its row; each other column is a series, named by its th. Put each number in a <data value> and write it as you want it read in the cell. Wrap the table in a .luz-table-wrap only when it can be wider than the screen, as the three-series example does, and give each td a data-label, as any core table does, so that on a narrow screen its rows stack and still name their cells. A table that always fits needs no wrapper: with one, the group, the region and the table would read the same name three times. The chart hides the wrapper with the table, and while it does the wrapper takes no Tab stop. LUZ draws no data of its own and invents none.

catalog.min.js loads the element’s own file, chart.min.js, when it scans the page; a page without catalog.min.js loads that file on its own. Link components/chart.css, after core’s.

The two types are an attribute, and so is the fill. The ratio is a property.

How it works

CSS from @luz-ds/catalog and a file of its own, @luz-ds/catalog/chart (dist/chart.min.js, under 3 kB compressed), which defines <luz-chart>. It uses no library and draws with DOM calls only, so a page that forbids inline scripts and styles runs it as it is. A bar of values compared by length does not need it: use the bar list, the column chart, the stacked bar or the heat map, which are CSS on a table or a list.

  • The table: it stays in the page. While the chart shows, the table is moved off screen, not hidden, so a screen reader reads it as it always did; when the button shows the table, the drawing goes. On paper, the table prints and the drawing does not.
  • The drawing: an SVG marked aria-hidden, drawn at its own size in pixels and again when the box changes size or the table changes. It has no animation, so there is nothing to stop under reduced motion. Series are --luz-chart-1 to --luz-chart-6, so a change of mode repaints nothing.
  • Telling series apart: each line ends in a mark of its own shape (a circle, a square, a triangle, a diamond, a plus and a cross) and the legend repeats it. In forced colors every line is the text colour, and each has its own dashes.
  • The numbers: the scale starts at zero, or lower when a figure is negative, and its steps are round (1, 2 or 5 times a power of ten). The figures on the axes are written with Intl.NumberFormat in the page’s language, such as 1.2K.
  • The words: the script writes none of its own. The button’s two words are yours, in data-luz-label-*; the title and the legend are copies of your caption and your column heads.

Without JavaScript

The table, or the list, is all there is, and it is complete: the caption, every figure, every name. The element is a block, the button does not exist and nothing is hidden. It does the same when the page lacks the table, and when type is not one of the two.

Keyboard and ARIA

  • Keys: Tab reaches the button; Enter or Space presses it, as on any button. The drawing takes no focus.
  • Name: the element is a group named by the table’s caption, and the button is described by it, so “Show table” is heard with what it shows. The drawing, its title and its legend are aria-hidden: the table says all of it.
  • Language: the words of the button, the caption and the names are yours. The numbers on the axes follow the language of the page.

Design

When to use

Use it to show how a few series change along an ordered axis, such as months, when the shape of the change is what the reader should see and you already have the numbers in a table. The small line (type="spark") is for a figure that needs its trend beside it.

When not to use

Do not use it when exact values matter more than the shape: a table says them better. For a few values compared on one scale, use a column chart or a bar list, which need no script.

  • Do not use it for parts of a whole: use a stacked bar. There is no pie or donut.
  • Do not use it for more than six series, or for series that cannot share a scale: split them into two charts.

It replaces a charting library that draws a canvas with no text beside it. Nothing in LUZ is removed.

Do and don't

Writing the content

The caption is the title of the chart, and says what is counted, where and when: “Parcels per route, January to June”. It is the name a screen reader gives the group.

  • Name each column as the legend should read, with its unit if it has one, and write each figure in its cell as you want it read: 1,204, not 1204, with the plain number in the value.
  • Write the button as the action and the thing: “Show table”, “Show chart”. Set both on the page, once, in its language.
  • Keep the names of the rows short: they are the labels of the X axis, and some are dropped when they do not fit.
