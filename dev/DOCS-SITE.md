## Vite config and the docs site generator

`root: <repo-root>` + `publicDir: false` → absolute paths like `/packages/...` and `/apps/...` in HTML resolve correctly in dev. The routes come from the plugin in `scripts/docs-site/` (`plugin.js` is the Vite glue, `catalog.js` the unit-tested logic, `html.js` a strict tokenizer); nothing is listed by hand:

- Every file under `apps/docs/pages/` is a page: `pages/index.html` → `/docs/`, `pages/a/b.html` → `/docs/a/b/`, `pages/a/index.html` → `/docs/a/` (an area index). Names starting with `_` are not pages. A page is a fragment: its content, under the generated h1. Front matter in a leading `<!-- luz:page -->` comment, one `key: value` per line: `title` (the h1, the start of `<title>`, the sidebar label), `description` (the lead under the h1 and the gallery line), `area` (an id of `site.json`, or `hub`) are required; optional `order`, `group` (a group of the area in `site.json`: a gallery heading, or the labelled "Helpers" sub-list), `files` (`;`-separated, shown in the page head), `module` (the JS module), `lead: false` (the content brings its own lead), `toc` (`h2` default, `h2,h3` — each h3 nested under its h2, used by component pages —, `false`), `generate` (`gallery` on an area index, `a-z`, `snippets`, `ai`, `notfound` on the 404).
- What the generator writes around the content, from the front matter of every page, in the markup of `@luz-ds/docs` (`body.o-shell.luz-docs-shell`, `aside.luz-docs-rail`, then `main.luz-docs-main`: "On this page" comes before the content): the sidebar (flat: every area of `site.json` with every page; `aria-current="page"` on the page, `"true"` on its area), the breadcrumb, the page head (`header.luz-docs-page-head`: the eyebrow "Area · Group" ("Area · package" on an area index, from the optional `package` of its area in `site.json`), the h1, the lead, a line "Files: …" on any other page with `files`, and, on a component or pattern page, the chips: its files, its module or "No JavaScript", the modes, "Tested" when `tests/<slug>.spec.js` or `tests/<area>-<slug>.spec.js` exists, its known issues), the rail ("On this page", with three or more h2 that have an id, a column from 80rem, above the content and folded by the docs script below it; then Copy page as Markdown, Edit this page, Report a problem), Previous / Next, the page foot ("Last updated", from `git log -1 --format=%cs`, today in dev), the galleries (where an area index has `<!-- luz:generated -->`, else after its content) and the A–Z index (`/docs/a-z/`). Every page is also published as `<route>index.md`, from the text of `llms-full.txt` (`renderPageMarkdown()` in `ai.js`). `apps/docs/404.html` becomes `/404.html`, with `<base href>` = `PAGES_BASE` (`vite.config.js`) and no script.
- The layout `apps/docs/_layouts/<layout>.html` wraps it. Templates know two things only: `<!-- luz:include <name> -->` (a file of `apps/site/_partials/`, which the home page and the docs share, or of `apps/docs/_partials/`; a name in both folders, or either folder being a symlink, fails the build; the landing includes the shared partials from `apps/site/_partials`) and a fixed set of `{{…}}` values (layouts and partials only). The landing includes the same `header` and `site-links` partials: Home, Docs and GitHub sit in the header row above 768px and in the drawer at 768px and below; the search button stays in the row at every width. The generator marks the current site links (`aria-current`).
- Dev server: route → file lookup table; a route without its trailing slash answers 301. Editing a layout, partial, page or `site.json` reloads the browser.
- Build: one entry per route (plus the landing at `/`); each HTML file is moved to `<route>/index.html`, and in the pages build its asset URLs and links between pages are relative to its depth.
- Search: the generator also writes `/docs/search-index.json` (`buildSearchIndex()`, from the same `indexData()` as the A–Z page, so the two never disagree), served by the dev middleware and emitted by the build. Every page gets the header's `<luz-search>` (`_partials/header.html`: the A–Z fallback link, the search button and the dialog, with `data-luz-search-src="/docs/search-index.json"` made relative in the pages build). The component is `@luz-ds/catalog/search`, imported at once by `apps/docs/reference.js` and `apps/landing/landing.js`; its fixed text is in the partial and the strings it writes are the dialog's `data-luz-label-*` (EX-005).
- Files for AI agents: `scripts/docs-site/ai.js`, from the same pages (RL-19), writes `llms.txt` (an index of every page), `llms-full.txt` (the curated text an agent needs to write the markup, under a ceiling: the accessibility statement is its outline and a pointer, and "Do and don't" and "Writing the content" stay on the pages), `examples/<area>/<slug>.html` (one standalone page of the markup of each component and pattern page) and copies the manifests to `/manifests/`: `classes.json` of every package and `custom-elements.json` of core and catalog, made at each package's build by `scripts/ai-manifests.js`. `generate: ai` is the page `get-started/ai.html` (Working with AI): the generator writes its files table and its rules table, from `aiArtifacts()` and from the registry of `@luz-ds/check` (`packages/check/src/messages.js`); `tests/working-with-ai.test.js` holds the rest of the page against the tool. The "For AI agents" block of each package README is written by `scripts/ai-readme.js`: never edit between its markers.
- Links: write internal links root-absolute with a trailing slash (`/docs/components/button/#how`). The build fails, with `file:line`, on a mis-nested tag, a duplicate id, an unknown route, a missing trailing slash or a `#fragment` that is not an id on the target page (a warning in dev).
- Languages: the home page is one template rendered once per language, `/` (English, the default), `/es/`, `/ar/`, each a static page with its own `lang`, `dir`, title, description and `<link rel="alternate" hreflang>` (plus `x-default`). See "Adding a language to the home page". The docs are in English, `/docs/…`, and in every language that has a folder `apps/docs/i18n/<code>/` (opt-in by folder): `/es/docs/…` today (Arabic is on the home page only, until its folder `apps/docs/i18n/ar/` exists; see `dev/TRANSLATING.md`), one route per English page, each with its own `lang`, `dir`, chrome (the catalog `apps/docs/i18n/<code>/strings.json`), `index.md` and `search-index.json`. A page with a translation file (`apps/docs/i18n/<code>/pages/…`) is in that language; every other page is its English content in the localized chrome, with `lang="en"`, a `canonical` link to the English page and a notice. A translation not yet reviewed shows its own notice. The language switcher of the header always goes to the same page in the chosen language. The 404 is one static file: English, plus a sentence in each other docs language with its own `lang` and `dir` and a link to its home; it has no script and no switcher. See "Adding a language to the docs" and "Translating a docs page".
